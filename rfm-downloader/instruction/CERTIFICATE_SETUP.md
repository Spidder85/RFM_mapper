# Установка и замена сертификата РФМ

Мануал для Windows и версии программы, использующей JCP + JTLS и
HDImageStore. Он охватывает установку на новом сервере и замену
сертификата на действующем. Основа — подтверждённый рабочий сценарий
импорта PFX через CSP с последующим использованием контейнера в JCP.

Примеры используют C:\RosFinMon и встроенный jdk-21.0.10.
Если каталог или версия Java отличаются, подставьте фактические значения
из run-rfm.bat. Названия окон могут отличаться между версиями CryptoPro.

## 1. Что подготовить заранее

- PFX/P12 с сертификатом и соответствующим закрытым ключом, пароль PFX
  либо совместимый файловый контейнер JCP с сертификатом.
- Серийный номер нового сертификата. Не путайте его с отпечатком
  сертификата, именем контейнера или номером лицензии.
- Пароль ключевого контейнера: он может отличаться от пароля PFX.
- Комплект приложения, Java 21, согласованные библиотеки JCP/JTLS
  и необходимые права использования этих компонентов.
- Windows-учётную запись, под которой будет запускаться задание.
- Доступ этой учётной записи к папкам downloads, logs, events,
  сетевым каталогам и сервису РФМ.

Файл .cer содержит только сертификат. Если соответствующий закрытый ключ
уже находится в JCP, сертификат можно установить к нему. Для нового сервера
одного .cer недостаточно. Неэкспортируемый ключ из реестра CSP нельзя
перенести только копированием сертификата; нужна доступная резервная копия
ключа либо выпуск нового ключа и сертификата.

До смены сертификата уточните у ответственного за доступ в РФМ,
допущен ли новый сертификат и требуется ли регистрация/замена привязки.
Этот мануал не заменяет процедуру выпуска сертификата в удостоверяющем центре.

Проверьте отдельно сроки сертификата, закрытого ключа и лицензий:
это разные сроки. Длинный срок сертификата не гарантирует такой же срок ключа.

## 2. Подготовка нового сервера

1. Разместите программу в C:\RosFinMon: JAR, libs, config, скрипты
   и используемую Java 21. Проверьте путь JAVA_HOME в run-rfm.bat.
2. Для описанного ниже импорта PFX должен быть установлен CryptoPro CSP,
   способный импортировать этот ГОСТ-ключ. Рабочая программа после импорта
   использует JCP, а не JCSP.
3. Откройте панель JCP под учётной записью будущего задания, указав
   ту же Java, что используется программой:

   ```bat
   cd /d "C:\RosFinMon\task\java-csp-5.0.49800-A"
   ControlPane.bat "C:\RosFinMon\jdk-21.0.10"
   ```

   Путь к комплекту панели приведён как пример. Не запускайте старый
   install.bat, использующий lib\ext и -Xbootclasspath/p, с Java 21.
4. Проверьте лицензию JCP и настройки JTLS в этой учётной записи.
   Наличие лицензии у администратора не подтверждает её доступность заданию.
5. На вкладке «Оборудование» посмотрите каталог HDImageStore.
   Значение с ${user.home} относится к профилю пользователя Java.
   Не подставляйте профиль администратора вместо профиля задания.

При переносе всей установки сохраните также state.properties, состояние
Zenith и очереди событий согласно действующей схеме развёртывания.
Не запускайте старый и новый загрузчики одновременно с общей очередью.

## 3. Импорт PFX с ключом

Выполняйте импорт под той же Windows-учётной записью, которая запускает программу.

1. Откройте PFX → мастер импорта сертификатов → «Текущий пользователь».
2. Укажите пароль PFX. Отметьте «Пометить этот ключ как экспортируемый»,
   если доступно и разрешено вашей политикой хранения ключей.
3. Выберите «Поместить все сертификаты в следующее хранилище» →
   «Обзор» → «Личное».
4. В появившемся окне CryptoPro «Выбор ключевого носителя»
   выберите «Директория». Имя нового контейнера может начинаться с pfx-.
   «Личное» — хранилище сертификатов Windows, «Директория» — носитель
   закрытого ключа. Это разные настройки.
5. Если предлагается задать пароль контейнера, сохраните его отдельно.
   Для программы нужен именно этот пароль.
6. Завершите импорт. В CryptoPro CSP → «Сервис» → «Протестировать»
   выберите новый контейнер и проверьте:
   - ключ доступен, проверка целостности и подписи успешны;
   - сертификат в контейнере соответствует закрытому ключу;
   - серийный номер и сроки соответствуют новому сертификату.

Имя HDIMAGE\… в отчёте — идентификатор носителя/контейнера, не полный
Windows-путь. Не считайте, что файлы автоматически оказались в C:\RosFinMon.
Исходный контейнер и резервный PFX сохраните до завершения проверки.

## 4. Проверка контейнера в JCP

1. В панели выберите «Хранилища ключей и сертификатов».
2. В списке провайдеров выберите
   «Java Cryptographic Provider (хэш, ЭЦП) и Crypto (шифрование)».
3. Раскройте HDImageStore и нажмите «Обновить».
4. Найдите новый контейнер → «Ключ обмена и сертификат».
   Должны отображаться и ключ, и сертификат. В «Просмотр»
   сверьте серийный номер.

Если контейнер не виден, сравните фактический каталог файлов контейнера
с каталогом HDImageStore на вкладке «Оборудование». При необходимости
перенесите папку файлового контейнера целиком поддерживаемым способом
в настроенный каталог JCP, сохранив исходную копию и ограничив доступ
учётной записью запуска. Не копируйте только .cer.

Если контейнер виден, но сертификата внутри нет, установите соответствующий
сертификат к существующему ключу через панель. Кнопка «Создать» создаёт
новый ключ и не восстанавливает ключ из .cer.

Успешный тест CSP и видимость в панели ещё не гарантируют работу TLS
через JCP — обязательна проверка программы ниже.

## 5. Настройки программы

В config\config.json замените раздел Certificate (заполнитель серийного
номера замените настоящим шестнадцатеричным номером без разделителей):

```json
"Certificate": {
  "SerialNumber": "NEW_CERTIFICATE_SERIAL_HEX",
  "UseCryptoPro": true,
  "CryptoPro": {
    "ProviderClasses": [
      "ru.CryptoPro.JCP.JCP",
      "ru.CryptoPro.Crypto.CryptoProvider",
      "ru.CryptoPro.ssl.Provider"
    ],
    "KeyStoreProvider": "JCP",
    "KeyStoreType": "HDImageStore",
    "KeyPasswordEnv": "RFM_KEY_PASSWORD",
    "SslProtocol": "GostTLSv1.2",
    "SslProvider": "JTLS",
    "KeyManagerAlgorithm": "GostX509",
    "KeyManagerProvider": "JTLS"
  }
}
```

Остальные рабочие настройки сохраните.

Переменная RFM_CERT_SERIAL имеет приоритет над SerialNumber из JSON.
При замене сертификата обновите её в окружении задания либо уберите
переопределение, если номер должен браться из config.json.
В текущем cmd убрать переопределение можно командой:

```bat
set "RFM_CERT_SERIAL="
```

KeyPasswordEnv содержит имя переменной, а не пароль.
Для проверки в одном окне cmd:

```bat
cd /d "C:\RosFinMon"
set "RFM_KEY_PASSWORD=YOUR_CONTAINER_PASSWORD"
call run-rfm.bat
echo Exit code: %ERRORLEVEL%
```

Замените YOUR_CONTAINER_PASSWORD паролем контейнера. Для пароля со специальными
символами cmd используйте принятый в организации способ передачи секретов,
не вставляйте его вслепую в командную строку.
Для контейнера без пароля удалите KeyPasswordEnv.
Credentials.Password — пароль учётной записи РФМ, он не заменяет пароль ключа.

## 6. Плановая замена сертификата

1. До истечения старого ключа подготовьте и проверьте новый контейнер
   по разделам 1, 3 и 4. Используйте отдельное имя контейнера.
2. На время переключения остановите расписание загрузчика и дождитесь
   завершения текущего запуска.
3. Сохраните рабочий config.json, настройки задания и способ передачи
   прежнего пароля. Сохраните старый контейнер в соответствии с политикой
   хранения ключей.
4. Обновите SerialNumber, при наличии RFM_CERT_SERIAL и пароль контейнера
   в окружении процесса. Для обычной смены сертификата пересобирать
   JAR или менять библиотеки не требуется.
5. Выполните проверку из раздела 7, затем возобновите расписание.

Текущая реализация выбирает сертификат по серийному номеру, не по имени
контейнера. При нескольких копиях одного сертификата выбирается первая
подходящая запись. Кроме того, JTLS KeyManagerFactory получает всё хранилище:
контейнеры со старыми/разными паролями могут мешать инициализации.
При такой ошибке используйте отдельный HDImageStore с нужным рабочим
контейнером; сохраняйте резервные контейнеры вне активного каталога,
а прежний путь запишите для возврата.

## 7. Проверка результата и автоматического запуска

- В логе зарегистрированы JCP, Crypto, JTLS, указаны источники библиотек.
- Открыто хранилище type=HDImageStore, provider=JCP.
- Выбран ожидаемый контейнер; номер сертификата соответствует конфигурации.
- Нет ошибок лицензии, пароля ключа и TLS; авторизация в РФМ успешна.
- Запуск завершился с кодом 0.

Если новых реестров нет, NO_UPDATES — нормальный результат.
Не удаляйте state.properties и события ради принудительного скачивания:
это может вызвать повторную обработку. При следующем обновлении проверьте
скачивание, публикацию события и обработку Zenith.

Отдельно запустите задание через Планировщик под его рабочей учётной записью.
Интерактивная команда set не передаёт пароль процессу Планировщика.
Обеспечьте RFM_KEY_PASSWORD в окружении задания способом, принятым в организации,
и проверьте его журнал и код завершения.
Убедитесь, что учётной записи доступны сетевые папки OutputDirectory и Events.

## 8. Возврат к прежнему сертификату

Если проверка не прошла, оставьте расписание остановленным. Верните
прежний SerialNumber/RFM_CERT_SERIAL, прежний пароль и при необходимости
прежний каталог HDImageStore. Проверьте запуск, затем включите расписание.

Возврат возможен только пока прежний сертификат/ключ действителен,
не отозван и допущен к работе в РФМ. Не удаляйте новый контейнер для
исправления настройки и не перезаписывайте исходные ключевые материалы.

## 9. Что записать после установки

- Серийный номер, имя контейнера и каталог HDImageStore.
- Windows-учётную запись, путь Java, версии JCP/JTLS.
- Сроки сертификата, закрытого ключа и лицензий.
- Дату проверки вручную и через Планировщик.
- Место защищённого хранения резервного PFX и пароля (не сам пароль).

Пароли, PFX и файлы ключевого контейнера не включайте в Git и общие журналы.

Разбор ошибок и сведения о переходе:
[JCP_MIGRATION.md](JCP_MIGRATION.md).
Готовый шаблон конфигурации:
