# Переход с JavaCSP на JCP

Для последующих установок на новом сервере и плановой замены сертификата
используйте [отдельный мануал](CERTIFICATE_SETUP.md).

Программа использует JCP + JTLS, хранилище HDImageStore. JavaCSP/JCSP
не регистрируется, не используется для чтения ключей и не входит в новый ZIP.
Проверки лицензии JCP сохраняются. Подключение к РФМ остаётся ГОСТ TLS
с клиентским сертификатом.

## 1. Подготовить ключевой контейнер на сервере

Выполнять под Windows-учётной записью, которая запускает run-rfm.bat
или задание Планировщика.

### Вариант A: есть PFX с закрытым ключом (проверенный сценарий)

1. Откройте PFX в Windows. Выберите «Текущий пользователь», введите пароль
   PFX и отметьте «Пометить этот ключ как экспортируемый», если доступно.
2. Выберите хранилище сертификатов «Личное».
3. В окне CryptoPro «Выбор ключевого носителя» выберите «Директория».
   Это место для ключевого контейнера; «Личное» — хранилище сертификатов.
   Запомните пароль контейнера, если он задаётся отдельно от пароля PFX.
4. В CSP → Сервис → Протестировать выберите созданный контейнер pfx-…
   и проверьте наличие ключа, соответствие сертификата и его серийный номер.
   Уникальное имя HDIMAGE… обозначает носитель, а не полный путь на диске.
5. Откройте панель JCP той же Java и под той же учётной записью. Выберите
   «Java Cryptographic Provider (хэш, ЭЦП) и Crypto (шифрование)» →
   «Хранилища ключей и сертификатов» → HDImageStore → «Обновить».
   Должны отображаться контейнер, ключ и нужный сертификат.
6. Если контейнер не появился, проверьте путь HDImageStore на вкладке
   «Оборудование» и фактическое расположение файлов контейнера. Не создавайте
   новый ключ вместо импортированного; не перезаписывайте исходный контейнер.

В рабочем случае этот импорт позволил использовать ключ в JCP, несмотря
на то, что другая его копия в реестре CSP была неэкспортируемой.
Это не означает, что неэкспортируемые ключи всегда можно перенести:
требуется уже имеющийся PFX с закрытым ключом и совместимый формат.
Файл .cer содержит только сертификат и для такого переноса недостаточен.

### Вариант B: есть экспортируемый контейнер CSP

1. В панели установленного CryptoPro CSP выберите Сервис → Скопировать
   и исходный контейнер сертификата РФМ. Сделайте копию на поддерживаемый
   файловый носитель средствами CSP. Исходный контейнер сохраните.
2. Копия должна содержать закрытый ключ и соответствующий сертификат
   (желательно всю цепочку). Один файл .cer не содержит закрытый ключ.
3. Откройте панель JCP через вашу Java 21. На вкладке «Оборудование»
   проверьте каталог HDImageStore. Импортируйте/скопируйте туда контейнер
   поддерживаемым способом; проверьте на вкладке «Хранилища ключей и
   сертификатов», что JCP видит сертификат и может использовать ключ.
   Путь задаётся в настройках JCP пользователя, не в OutputDirectory.
4. Если CSP запрещает экспорт/копирование ключа либо JCP не читает формат
   контейнера, переход с этим ключом ещё не готов. Нужен совместимый
   экспортируемый контейнер или перевыпуск ключа/сертификата для JCP.
   Новое имя провайдера в config.json не решает это ограничение.

Панель следует запускать из папки комплекта JCP, например:

```bat
cd /d "C:\RosFinMon\task\java-csp-5.0.49800-A"
ControlPane.bat "C:\RosFinMon\jdk-21.0.10"
```

Это путь к использованному комплекту панели. В ней выбирается провайдер
JCP; наличие JavaCSP в комплекте не означает его использование приложением.

Проверьте лицензию JCP под этой же учётной записью. Не используйте старый
install.bat 2014 года для JDK 21. Установка через другую Java/пользователя
не подтверждает готовность лицензии у рабочего процесса.

## 2. Настроить config.json

Сохраните текущие Credentials, SerialNumber, OutputDirectory, Events и
остальные рабочие настройки. В Certificate оставьте UseCryptoPro=true.
Замените только объект Certificate.CryptoPro:

```json
{
  "ProviderClasses": [
    "ru.CryptoPro.JCP.JCP",
    "ru.CryptoPro.Crypto.CryptoProvider",
    "ru.CryptoPro.ssl.Provider"
  ],
  "KeyStoreProvider": "JCP",
  "KeyStoreType": "HDImageStore",
  "KeyPasswordEnv": "RFM_KEY_PASSWORD",
  "SslProtocol": "GostTLSv1.2",
  "SslProvider": "JTLS",
  "KeyManagerAlgorithm": "GostX509",
  "KeyManagerProvider": "JTLS"
}
```

KeyPasswordEnv — **имя переменной окружения, не сам пароль**.
Шаблон предполагает пароль контейнера. В одном окне cmd выполните:

```bat
cd /d "C:\RosFinMon"
set "RFM_KEY_PASSWORD=YOUR_CONTAINER_PASSWORD"
call run-rfm.bat
```

Замените YOUR_CONTAINER_PASSWORD паролем контейнера. Отсутствие настроенной
переменной вызывает явную ошибку. Для контейнера без пароля удалите
KeyPasswordEnv: тогда используется пустой пароль.

Команда set не сохраняет переменную после закрытия cmd и не передаёт её
уже работающему Планировщику. Для автоматического запуска обеспечьте
RFM_KEY_PASSWORD в окружении процесса задания и доступ к HDImageStore
под учётной записью задания. Не публикуйте пароль или PFX в Git.

В актуальном run-rfm.bat предусмотрен вариант без ручного set: создайте
config\rfm-key-password.local в каталоге приложения. Первая строка — пароль
контейнера. В дистрибутиве уже есть пустой файл из шаблона: заполните его
при первой установке; при обновлении сохраните существующий рабочий файл.
Первая строка — пароль
контейнера без кавычек и команды set; кодировка UTF-8 без BOM. Скрипт
загрузит его в RFM_KEY_PASSWORD, если переменная ещё не задана.
Существующий пустой/нечитаемый файл приводит к остановке. Если файла нет,
скрипт оставляет проверку настроенной переменной приложению; контейнеры
без пароля с удалённым KeyPasswordEnv продолжают работать.
Файл содержит открытый пароль: права только для учётной записи запуска
и администраторов; *.local исключён из Git. Для задания используйте
актуальный run-rfm.bat из проекта, заменив старый run.bat в настройках задачи.

## 3. Собрать и развернуть

```bat
mvn -pl rfm-downloader -am test package
```

Сохраните резервные копии рабочего JAR, config.json, run-rfm.bat и libs.
Перенесите rfm-downloader/target/rfm-downloader.jar в C:\RosFinMon
и обновите run-rfm.bat. Используйте согласованный комплект библиотек JCP/JTLS.
Обновлять библиотеки повторно только ради ввода лицензии не требуется.
JCSP.jar и sspiSSL.jar уберите из активной libs в резервный каталог вне
classpath. Остальные зависимости приложения сохраните.

В java.security используемой JVM не должно быть глобальной регистрации
JCSP. Если она есть, программа сообщит об этом явно; используйте отдельную
Java 21 для приложения без такой регистрации.

## 4. Проверить

После запуска ожидаются JCP/JTLS и их фактические версии/пути в логе,
затем KeyStoreType=HDImageStore, KeyStoreProvider=JCP.
Ошибка Certificate not found означает, что сначала надо закончить перенос
контейнера/сертификата для учётной записи запуска.
Успешная загрузка сертификата ещё не подтверждает TLS: проверьте успешную
авторизацию в РФМ и полный цикл скачивания/обработки.

15.09.2026 пользователь подтвердил успешный запуск на сервере после импорта
PFX и исправления KeyPasswordEnv: в JSON указано имя RFM_KEY_PASSWORD,
а пароль передан через set в том же окне cmd. Это подтверждение рабочего
запуска пользователя; автоматические тесты не обращаются к продуктивному РФМ.

## 5. Типичные ошибки

| Сообщение / симптом | Что проверить |
| --- | --- |
| Certificate not found in JCP key store | Контейнер и сертификат должны быть видны в HDImageStore нужного пользователя. |
| Key password environment variable is not set: RFM_KEY_PASSWORD | Переменная не передана процессу запуска. |
| Key password environment variable is not set: 123 | В KeyPasswordEnv записан пароль вместо имени переменной; исправьте JSON и сохраните файл. |
| Ошибка пароля при чтении ключа | Нужен пароль контейнера, не обязательно пароль исходного PFX. |
| В стеке по-прежнему ru.CryptoPro.JCSP | Проверить развёрнутый JAR, старую конфигурацию и глобальные провайдеры JVM. |
| LicenseException в новом JCP-сценарии | Проверить лицензию именно JCP под учётной записью запуска; обновление JAR не продлевает лицензию. |
| Панель видит контейнер, задание — нет | Сравнить пользователя, Java и настройки HDImageStore интерактивного запуска и Планировщика. |
